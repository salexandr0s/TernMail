# Organize Mail

Organize Mail builds a label and rule plan from the selected Google account's mail and existing setup. Open **Settings → Organize Mail**, choose an account and scan size, and select **Analyze mail**. The default scan includes up to 5,000 received and sent messages combined; options cover 1,000, 20,000 and 100,000 messages. These are limits, not minimums: smaller mailboxes use their actual message count, including a final short batch. An empty mailbox shows a normal empty state without an AI request. The account must be enabled for the assistant and ChatGPT must be connected with an available model. Gmail Settings access allows the job to inspect existing filters and propose additions.

The analysis uses senders, recipients, subjects, dates, existing labels and filter settings, bounded message previews, and mailing-list/automation hints. It does not download bodies or attachments. This information goes to the connected ChatGPT account during the job. Tern anchors the Gmail listing to the job's start time, pages through the selected window, and sorts its messages by date. Drafts, spam, trash, and chat messages are excluded. A smaller mailbox uses the messages available. The review distinguishes reaching the scan limit from incomplete reads; retained sample data also has a 256 MiB limit.

The job reads the account's labels and rules, discovers patterns in batches of 200 messages, combines related findings, and rechecks every batch against the shared plan. Progress shows the current stage, completed batches and elapsed time. Larger scans can take a while. Analysis continues when you leave the pane or close Settings; reopening it shows the current progress or review. **Cancel** or Escape discards the analysis. Nothing changes in Gmail during this step.

Successful analysis requests are checkpointed in memory. If a later request fails, **Resume analysis** keeps the same sample and reuses the completed requests. Checkpoints bind the sampled content, model, labels and rule catalogue, including whether rule access was available. Quitting Tern discards them. A failed metadata read can produce an explicitly incomplete sample; a failed rule-catalogue request requires retry rather than pretending the account has no rules.

Review uses decision cards rather than individual email lists. Each card shows its target label, why it is suggested, and independent choices for future-mail rules and back-tagging. The rule choice shows the sender match and label action. Back-tagging adds the label only to matching messages from this scan; turning it off leaves existing mail unchanged while the future rule is created. Labels without a recurring sender rule have a back-tagging choice only. Exact sender details and a new label's editable name are available in a compact disclosure. Existing labels retain their names and IDs.

**Select all** chooses the available actions; **Clear selection** declines them. Either checkbox can be selected again after both are cleared. Changing a proposed label name to an already covered label removes an unnecessary future-rule choice. The footer shows the actual new rule and back-tagging counts before **Apply to Gmail**. **Start Over** discards the review. Applied cards summarise the chosen actions without email-level detail.

Existing user labels retain their IDs and names. When back-tagging is selected, applying adds labels to the matching sample messages. It does not archive, delete, mark messages read, or remove existing labels.

Categories with consistent recurring senders can also create Gmail filters. Each new filter only adds its category label to future incoming mail from an exact sender. Existing filters and their actions stay in place. For an existing label, additional sender filters extend its coverage without widening any forwarding, archive or deletion rule. Exact sender coverage already present is reused. Filters require Gmail Settings permission in **Connections** and a complete sample. A sender needs incoming examples in at least two separate conversations, mailing-list or automation evidence on every incoming example, and consistent category membership across all inspected incoming mail. Sampled replies to that sender or in those conversations exclude a future rule. Evidence is checked across all batches, so a contradictory example in a later batch can remove a proposed rule. Personal correspondence, mixed-purpose senders, and one-off mail can still receive labels on the reviewed messages.

Action and Waiting describe the reviewed sample. They require evidence of a request or expected reply, use the uniquely newest sampled message in a conversation, and do not create recurring sender filters. Missing dates or tied newest timestamps prevent a workflow suggestion for that conversation. They do not automatically clear when a reply arrives. Analyze again to review newer mail; previously applied labels remain until removed through normal label controls.

The labels and filters are saved in Gmail, so they also work in Gmail's website and other mail clients. Gmail filters handle incoming messages; they do not infer whether a conversation needs a reply. See [Google's filter guide](https://developers.google.com/workspace/gmail/api/guides/filter_settings).

## How suggestions are chosen

Discovery requests identify candidate themes in each batch. A candidate can have one conversation at this stage: support for the same theme may appear in another batch. Semantic consolidation groups validated candidate references, while Swift keeps their exact message identities. The job compares the complete existing label and rule catalogues in bounded partitions, then checks every mail batch against the resulting taxonomy. The final plan contains at most 40 categories.

Existing labels keep their complete names and stable IDs. After the combined audit, new topic labels need support from at least two separate conversations; reusing an existing label or suggesting Action/Waiting can use one message. The model is instructed to avoid redundant names, catch-all categories, quoted old requests, and promotional calls to action. Workflow suggestions require an unresolved request or expected response, excluding informational mail, acknowledgments and completed work. These semantic judgments still depend on the available previews and model.

After analysis, Tern drops unsupported new topics, stale or wrong-direction workflow messages, and unsupported sender rules. Useful classifications remain available for review. Invalid names, malformed output, unknown message IDs, and multiple topics or conflicting states on one message are still rejected. A message can have one topic plus one state. Uncertain messages can remain unassigned.

The organizer requests `List-Id`, `List-Unsubscribe`, and `Auto-Submitted` metadata. It converts these to two booleans; raw list identifiers and unsubscribe URLs are not sent to the model or stored by this feature. Nonempty list markers indicate mailing-list evidence; recognized `auto-generated` and `auto-replied` values indicate automation. `Auto-Submitted: no` does not. These are delivery hints, not proof of a topic or outstanding task. See [List-Id](https://www.rfc-editor.org/rfc/rfc2919.html), [List-Unsubscribe](https://www.rfc-editor.org/rfc/rfc2369.html), and [Auto-Submitted](https://www.rfc-editor.org/rfc/rfc3834.html).

## Delivery and recovery

Apply re-fetches labels and filters before saving the selected changes to Tern's existing action queue. An existing label that changed or disappeared needs renewed review. Removed existing sender coverage cannot silently turn into an unreviewed new rule. Current and queued filters count toward Gmail's 1,000-filter limit. Label creation runs before message labeling and dependent filters; message changes use queue chunks of at most 1,000 IDs. The review distinguishes queued work from confirmed delivery and failed changes. A network interruption can leave work queued; it is retried by the normal sync engine. Failed changes can be inspected and retried in **Settings → Failed Changes**.

Delivery progress counts queued changes, which can include label creation, message labeling, and filters. The completion summary shows only the labels and messages selected for that application. If a saved action can no longer be confirmed, check the account in Gmail before starting again. **Back to start** leaves the delivery screen; accepted queue work continues.

Analysis results and review edits remain in memory for each account while Tern is open. Leaving the pane, closing Settings, or switching accounts preserves them. **Cancel**, **Start Over**, or **Back to start** discards the session. Removing an account or changing assistant access, the ChatGPT connection, or the selected model clears its review. Quitting Tern also discards these sessions. Ordinary message metadata remains in the mail cache. Changes already accepted into the action queue retain the user's Apply instruction and continue through normal delivery. If Tern knows a newer conversation message arrived after an Action or Waiting suggestion, Apply asks for a new analysis.

## Implementation

- `SyncEngine.organizationSamples` reads a bounded, paged Gmail metadata sample and current rule context, checks access around progress callbacks and responses, and upserts each metadata chunk without replacing threads or advancing the history cursor. Sampling progress counts attempted reads, including unavailable messages. Sample cache holds renew while the retained analysis runs.
- The Foundation-only `MailOrganization` target contains the shared `OrganizationEvidence` helper; it adds no external dependencies or persistent state.
- `MailOrganizationJobAnalyzer` coordinates discovery, semantic consolidation, catalogue comparison, batch audits and global validation. Each request has a JSON schema and no tools. Sample, label and filter text is untrusted data. Every request and response is bounded independently; checkpoint entries contain only successful, validated responses. The legacy single-batch `MailOrganizationAnalyzer` remains available separately.
- `SyncEngine.applyOrganization` validates the selected plan and account, adopts existing labels, and queues the chosen additive message and filter changes together. Rules-only choices retain the complete message evidence for validation while skipping message modifications. Receipts count only actual back-tagging selections. Filter payloads participate in temporary-label resolution and cross-lane queue ordering.
- `MailOrganizationModel` binds a review to the account instance, assistant permission revision, ChatGPT connection revision, and selected model. Late progress callbacks cannot restore a canceled or superseded analysis. Its UI edits do not call Gmail until Apply.

Tests cover broad paging, mixed received/sent samples, incomplete reads, revoked access, invalid model output, cross-batch evidence, checkpoint resume, stable label identities, existing-rule preservation, filter budgets, label dependencies, duplicate prevention, and delivery outcomes. Google API behavior follows the [message listing](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [message label modification](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/batchModify), and [filter creation](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.filters/create) contracts.
